# RightToken 用户地区分配与人工改派设计

## 1. 目标

为用户运营后台补齐完整的客户负责人分配闭环：

- 新用户首次进入召回后台时，系统必须自动完成负责人分配。
- 自动分配以用户运营归属地为主要依据，省 / 州 / 地区优先于国家。
- 地区无法识别或没有规则命中时，由主管理员自动暂管，不能产生无人负责的用户。
- 主管理员和管理员可以在自动分配后人工调整负责人。
- 人工调整后，人工结果具有最高优先级，数据同步、地区变化和规则重算都不能覆盖。
- 管理员明确执行“恢复自动分配”后，系统才重新使用当前地区规则计算负责人。
- 用户负责人变化时，同步处理该用户尚未完成的运营任务，并保留完整审计记录。

## 2. 现状与问题

系统当前已经具备：

- 邮箱域名优先、注册 IP 兜底的运营归属地判定。
- 按国家、省 / 州 / 地区匹配负责人。
- 主要负责人、后备负责人、负载上限和主管理员兜底。
- 分配预览、规则发布和全量重算。
- `UserProfile.ownerId` 用户负责人字段。
- 任务转派和操作记录。

当前缺口是：

- “成员与权限”页面没有展示或配置运营人员负责地区，管理员难以建立成员与客户范围的关系。
- 用户详情只能查看负责人，不能人工改派或恢复自动分配。
- `ownerId` 无法区分系统分配与人工分配。
- 规则重算会覆盖 `ownerId`，无法保护人工改派结果。
- 地区无法识别时的页面表达和处理方式不够明确。
- 用户负责人变化与未完成任务负责人变化没有统一的事务边界。

## 3. 方案选择

### 方案 A：增强现有分配引擎并增加人工锁定（采用）

继续以 `AssignmentRule` 作为唯一自动分配规则来源，在“成员与权限”页面增加便捷的负责地区配置入口，同时增加用户人工改派状态。

优点：

- 复用当前已经完成并有测试覆盖的匹配、预览、发布和重算逻辑。
- “成员负责地区”和“分配规则”不会形成两套互相冲突的数据。
- 可以继续使用省份优先、国家次之、后备负责人和主管理员兜底。
- 改动范围可控，适合现有测试服务器快速修复。

### 方案 B：直接在成员表保存国家和省份

给每个运营成员增加国家和省份数组，运行时绕过 `AssignmentRule` 直接匹配。

不采用原因：

- 与现有分配规则重复。
- 无法自然表达顺序、后备负责人和负载上限。
- 后续很容易出现成员页面和分配规则页面结果不一致。

### 方案 C：只按国家建立固定映射

每个国家只配置一个运营人员，不支持省份优先或复杂范围。

不采用原因：

- 无法满足省份为最小单位的现有业务要求。
- 不能覆盖中国、美国等需要区域拆分的运营场景。

## 4. 自动分配流程

### 4.1 首次进入

新用户同步到召回后台后按以下顺序处理：

1. 保存用户注册、支付、余额、调用和注册 IP 等事实数据。
2. 使用邮箱域名规则判断运营归属国家。
3. 邮箱规则未命中时，使用注册 IP 的本地 GeoIP 数据判断国家和省 / 州 / 地区。
4. 以最终运营归属地运行负责人分配规则。
5. 优先匹配省 / 州 / 地区规则。
6. 未命中省份规则时匹配国家规则。
7. 规则主要负责人不可用时使用后备负责人。
8. 地区无法识别、没有规则命中或规则负责人不可用时，由当前有效主管理员暂管。
9. 写入用户负责人、分配方式、分配原因和分配时间。
10. 后续生成的运营任务默认交给该用户负责人。

系统不得因为地区无法识别而等待人工完成首次分配。

### 4.2 自动重新计算

以下场景可以触发自动重新计算：

- 管理员发布新的地区分配规则。
- 用户运营归属地发生变化。
- 管理员执行全量负责人重算。
- 已停用成员的用户需要重新分配。
- 管理员对某个用户执行“恢复自动分配”。

自动重新计算只处理处于“系统分配”状态的用户。人工锁定用户必须跳过。

## 5. 人工改派

### 5.1 操作入口

主管理员和管理员可以从以下入口调整用户负责人：

- 用户中心列表中的“调整负责人”。
- 用户详情中的负责人区域。

操作表单包含：

- 当前负责人。
- 新负责人。
- 调整原因，必填。
- 提示“人工调整后，自动规则不会覆盖该负责人”。

普通运营人员不能调整客户负责人。

### 5.2 人工锁定

人工改派成功后：

- 用户负责人更新为所选成员。
- 分配方式更新为“人工分配”。
- 记录操作管理员、原因和时间。
- 所有未完成任务同步转移给新负责人。
- 已完成、已取消任务只保留历史负责人，不修改。
- 后续用户同步、地区变化和规则重算跳过该用户。

为了避免出现半完成状态，用户负责人更新、未完成任务转移和审计记录必须在同一个数据库事务内完成。

### 5.3 恢复自动分配

人工分配用户显示“恢复自动分配”操作。

管理员确认后：

1. 解除人工锁定。
2. 使用当前用户运营归属地和最新生效规则重新计算负责人。
3. 更新用户负责人和所有未完成任务。
4. 记录恢复前负责人、恢复后负责人、执行人和时间。

恢复操作不是简单清空负责人，完成后必须立即得到一个系统负责人。

## 6. 数据设计

在 `UserProfile` 增加：

- `ownerAssignmentMode`：`AUTO` 或 `MANUAL`，默认 `AUTO`。
- `ownerAssignedAt`：最近一次负责人确定时间。
- `ownerAssignedById`：人工调整的管理员；系统分配时为空。
- `ownerAssignmentReason`：面向运营的分配说明。

增加 `OwnerAssignmentMode` 枚举。

`ownerAssignedById` 关联 `Member`，成员被停用时保留用户的负责人分配历史，不级联删除用户。

所有负责人变化同时写入 `AuditLog`：

- `user.owner_auto_assigned`
- `user.owner_manually_assigned`
- `user.owner_auto_restored`
- `user.owner_reassigned_after_member_revoked`

审计元数据包括：

- 原负责人。
- 新负责人。
- 分配方式。
- 地区快照。
- 命中规则。
- 人工原因。
- 被转移的未完成任务数量。

## 7. 成员与权限页面

### 7.1 成员列表

运营人员行增加：

- 负责国家。
- 负责省 / 州 / 地区。
- 当前负责用户数。
- “设置负责地区”操作。

管理员和主管理员仍显示全局权限，不要求配置负责地区。

### 7.2 设置负责地区

“设置负责地区”打开紧凑编辑区：

- 可选择一个或多个国家。
- 可在国家下填写或选择省 / 州 / 地区。
- 可设置后备负责人。
- 可查看预计覆盖用户数。
- 保存前展示受影响用户数量。

该入口编辑的仍是现有 `AssignmentRule`，不是成员表中的第二套规则。

同一具体省份只能有一个主要负责人。发生冲突时阻止保存，并明确显示冲突成员和地区。

国家规则可以与省份规则同时存在，省份规则永远优先。

### 7.3 分配规则页面

保留现有“客户分配”页面作为全局管理入口：

- 查看所有地区与负责人映射。
- 调整判断顺序。
- 设置后备负责人和负载上限。
- 预览分配结果。
- 发布并重算所有“系统分配”用户。

成员页面和分配规则页面必须调用同一套接口和校验逻辑。

## 8. 用户页面

### 8.1 用户列表

负责人列显示：

- 负责人姓名。
- “系统分配”或“人工分配”状态。

主管理员和管理员可以直接点击“调整负责人”。

地区不明确但由主管理员暂管时，显示：

- 运营归属：“暂未识别”。
- 负责人：“主管理员”。
- 分配说明：“地区暂未识别，由主管理员暂管”。

不得显示“公共池”“NULL”“未命中规则”等后端语言。

### 8.2 用户详情

负责人区域显示：

- 当前负责人。
- 分配方式。
- 最近分配时间。
- 面向运营的分配说明。
- 管理员操作按钮。

人工分配时额外显示：

- 调整人。
- 调整原因。
- “恢复自动分配”。

## 9. 权限

### 主管理员

- 查看全部用户、任务、邮件和分配规则。
- 设置所有运营人员负责地区。
- 人工调整任意用户负责人。
- 恢复自动分配。
- 发布规则并执行全量重算。

### 管理员

- 查看全部用户、任务、邮件和分配规则。
- 设置运营人员负责地区。
- 人工调整任意用户负责人。
- 恢复自动分配。
- 发布分配规则。

### 运营人员

- 只查看自己负责的用户及相关任务、邮件。
- 不能设置地区规则。
- 不能人工改派客户。
- 不能恢复自动分配。

## 10. 成员停用

撤销运营人员权限时：

1. 立即停用该成员并注销会话。
2. 找出该成员负责的所有用户。
3. 对“系统分配”用户按当前地区规则重新计算。
4. 对“人工分配”用户解除原失效负责人，并交给主管理员暂管，保留“原人工负责人已停用”的审计说明。
5. 将所有相关未完成任务同步交给新的负责人。
6. 记录处理用户数、任务数和失败数。

不能简单把 `ownerId` 清空后留下无人负责用户。

## 11. 失败处理

- 自动分配找不到主管理员时，用户同步应记录严重配置错误，不能静默写入无人负责状态。
- 人工调整的目标成员必须为有效的管理员或运营人员。
- 规则冲突、失效负责人或事务失败时，不得保存部分结果。
- 批量重算中单个用户失败不阻塞其他用户，但失败用户保持原负责人并进入可重试记录。
- 页面只展示运营可理解的失败原因，技术错误写入服务日志。

## 12. 兼容与迁移

数据库迁移后：

- 现有 `ownerId` 不为空的用户默认标记为 `AUTO`。
- 现有 `ownerId` 为空的用户立即运行一次自动分配。
- 现有规则继续生效。
- 不修改已完成任务的历史负责人。

首次部署执行：

1. 数据库迁移。
2. 校验有效主管理员存在。
3. 预览现有规则覆盖结果。
4. 对所有非人工锁定用户执行一次负责人重算。
5. 核对用户总数、自动分配数、主管理员暂管数和失败数。

## 13. 验收标准

1. 新用户首次同步后必定有负责人。
2. 省份规则优先于国家规则。
3. 地区无法识别时自动由主管理员暂管。
4. 在成员页面可以配置运营人员负责国家和省份。
5. 管理员可以从用户列表和详情人工改派。
6. 人工改派后，地区变化和全量重算不会覆盖负责人。
7. 恢复自动分配后，立即按最新规则产生负责人。
8. 用户负责人变化后，所有未完成任务同步转移。
9. 停用运营人员后，不产生无人负责用户。
10. 普通运营只能看到自己负责的用户，不能修改分配。
11. 所有负责人变化都有可追溯的审计记录。
12. 页面不暴露数据库字段、空值、规则内部表达式或技术错误码。

## 14. 测试范围

### 单元测试

- 省份规则优先于国家规则。
- 未识别地区使用主管理员。
- 人工锁定跳过自动重算。
- 恢复自动分配重新运行规则。
- 停用成员后的负责人选择。

### 集成测试

- 新用户同步、归属地判断和首次分配。
- 人工改派事务同时更新用户、任务和审计。
- 规则发布只重算自动分配用户。
- 恢复自动分配更新用户及未完成任务。
- 成员停用后批量重新分配。
- 管理员和运营人员权限边界。

### 页面测试

- 成员负责地区的查看和编辑。
- 用户列表人工改派入口。
- 用户详情人工状态及恢复按钮。
- 普通运营不显示管理操作。
- 所有提示使用运营语言。
