# 撤销成员权限时指定接管人

## 目标

撤销运营人员或普通管理员的运营后台权限前，管理员必须指定一名当前启用的
成员作为接管人。系统在同一个事务中停用原成员、撤销其会话，并把其负责的
全部客户和所有未完成任务交给指定成员，避免产生无人负责的客户或任务。

## 交互设计

成员列表中的“撤销权限”按钮打开确认区，不再直接执行撤销。

确认区包含：

1. 原成员姓名、邮箱、负责客户数和未完成任务数。
2. 必填的“工作接管人”选择框。
3. 接管人按“姓名 · 邮箱 · 角色”显示。
4. 只列出当前启用且不是被撤销成员的成员。
5. 未选择接管人时，“确认撤销并交接”按钮不可用。
6. 明确提示：客户及未完成任务会转给接管人，已完成和已取消任务只保留
   历史，不会更改。

主管理员可以撤销普通管理员或运营人员。普通管理员只能撤销运营人员。
接管人可以是启用状态的主管理员、管理员或运营人员。

## API 约定

`DELETE /api/members/:id/access` 接收 JSON：

```json
{
  "successorId": "member-id"
}
```

接口执行以下校验：

- 操作人拥有成员管理权限。
- 被撤销成员存在、处于启用状态，且不是操作人或主管理员。
- 接管人存在、处于启用状态，且不是被撤销成员。
- `successorId` 缺失或无效时拒绝撤销，不允许自动回退到无人负责状态。

稳定错误码：

- `SUCCESSOR_REQUIRED`
- `SUCCESSOR_NOT_FOUND`
- `SUCCESSOR_INACTIVE`
- `SUCCESSOR_SAME_AS_TARGET`

## 数据交接

整个交接在一个数据库事务内完成：

1. 停用被撤销成员并删除其全部运营后台会话。
2. 查询所有 `ownerId` 为被撤销成员的有效客户。
3. 将这些客户的负责人改为接管人。
4. 所有交接客户设置为 `MANUAL`，记录交接时间、操作人和原因
   “原负责人权限已撤销，由指定成员接管”。
5. 将这些客户名下所有未完成任务转给接管人，保留任务当前状态。
6. 处理历史脏数据：仍直接指派给被撤销成员、但不在上述客户集合内的
   未完成任务，也转给接管人。
7. 已完成和已取消任务不修改负责人。
8. 写入逐客户审计记录和成员撤权汇总审计记录。

任何一步失败，整个事务回滚：成员权限、客户负责人和任务负责人都保持原状。

## 后续自动分配

本次交接属于管理员明确的人工操作。所有交接客户设置为人工指定模式，因此
后续 RightToken 同步、地区识别、分配规则发布和全量重算都不会覆盖接管人。

管理员仍可在用户详情中单独调整负责人，或点击“恢复自动分配”，让特定客户
重新按照最新地区规则分配。

## 返回结果

接口返回：

```json
{
  "revokedSessions": 2,
  "reassignedUsers": 35,
  "transferredTasks": 18,
  "successor": {
    "id": "member-id",
    "displayName": "接管人",
    "email": "operator@example.com"
  }
}
```

成功后成员页面刷新，原成员显示为停用，接管人的负责客户数和未完成任务数
同步更新。

## 测试范围

- 未选择接管人时前端不能提交，接口也拒绝请求。
- 不能选择被撤销成员本人、停用成员或不存在的成员。
- 管理员不能越权撤销其他管理员。
- 客户全部变为指定接管人和人工指定模式。
- 未完成任务全部转移且状态保持不变。
- 已完成和已取消任务保持原负责人。
- 事务中任一步失败时撤权和交接全部回滚。
- 页面向接口提交正确的 `successorId`，成功后刷新成员统计。
