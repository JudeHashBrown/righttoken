# F 组异常详情设计

## 背景

RightToken 源库会依据连续失败次数和近 30 分钟失败率识别服务异常，但召回管理台目前只同步 `anomalyActive` 与 `anomalyChangedAt`。因此 F 组用户、用户详情和自动紧急任务都只能显示泛化的“系统发现异常”，运营无法判断该处理什么问题。

## 目标

- F 组用户列表直接显示一行可行动的异常摘要。
- 用户详情展示异常分类、状态码、错误类型、模型、平台、失败统计和最近发生时间。
- F 组自动紧急任务保存同一份具体原因。
- 异常解除后不再显示“当前异常”，已有任务和分组历史保留触发时的原因。

## 数据设计

源数据库查询继续使用现有异常判定口径，并从最新一条符合判定条件的 `ops_error_logs` 记录提取：

- `error_phase`
- `error_type`
- `error_owner`
- `status_code`
- `model`
- `platform`
- 最近 30 分钟请求数与失败数
- 当前连续失败数
- 最近异常时间

召回库在 `UserProfile` 上保存结构化异常快照。源适配器使用一个可空的 `anomalyDetail` 对象传递这些字段；非数据库适配器可不提供该对象。异常未激活时清空当前异常快照。

不读取、不保存也不展示 `error_message`、请求正文、响应正文、请求头、令牌、密钥或供应商原始详情。异常说明只由错误归属、阶段、状态码、供应商错误码、网络错误类型、模型、平台和失败统计等结构化字段生成。

## 展示设计

异常展示由纯函数统一生成，避免三个页面各自拼接不同文案。

- 分类优先使用 `error_owner` 和 `error_phase`，输出“上游服务异常”“平台路由异常”“平台内部异常”或“网络异常”。
- 摘要示例：`上游服务异常 · HTTP 502`。
- 统计示例：`近30分钟失败 4/5 · 最近发生 15:42`。
- 任务原因示例：`上游服务异常（HTTP 502），近30分钟5次请求失败4次。`
- 字段不足时至少显示连续失败次数或异常发生时间，不展示未经验证的源错误文本。

用户列表在 F 组胶囊下显示摘要和统计。用户详情在“用户概况”前部显示“当前异常”区域。任务创建时把统一生成的任务原因写入 `RecallTask.reason`。

## 异常生命周期

- `anomalyActive=true`：保存并显示当前异常详情。
- `anomalyActive=false`：清空 `UserProfile` 当前异常字段。
- 从其他组进入 F：`reasonLabel` 与 `SegmentHistory.reason` 使用具体异常摘要。
- 已创建的紧急任务保留触发时的具体原因，即使异常随后解除。

## 测试

- 数据库适配器：验证 SQL 提取字段、数据类型转换和快照内容。
- 同步：验证异常详情写入及异常解除后清空。
- 文案：验证分类、摘要、统计、任务原因和缺失字段降级。
- 分组和任务：验证 F 组原因进入 `reasonLabel`、历史和紧急任务。
- UI：验证用户列表和用户详情渲染异常信息。
- 完整验证：单元测试、集成测试、类型检查、代码检查、构建及 localhost 页面检查。
