# 邮箱收信同步状态修复设计

## 背景

邮箱连接测试和 SMTP 发信均正常，但邮箱工作台仍显示“尚未运行同步”。当前页面还会在 `lastSyncedAt` 为空时显示“同步正常”，并将连接测试写入的 `lastSuccessAt` 标注为“最近成功收信”，导致管理员无法判断是否真正执行过 IMAP 收信。

自动收信由独立的 `recall-worker` 每两分钟执行。只要同步任务成功运行，即使没有新邮件，`lastSyncedAt` 也应更新。因此，“从未同步且没有错误”表示同步任务尚未执行，而不是同步正常。

## 目标

1. 准确区分连接测试成功和邮件同步成功。
2. 从未同步时不再显示“同步正常”。
3. 最近一次成功同步超过十分钟时，提示检查后台 Worker。
4. 明确告诉管理员“测试连接”不会收取邮件，以及如何手动触发首次同步。
5. 保留现有 SMTP、IMAP、邮件保存、回复匹配和两分钟自动同步机制。

## 非目标

- 不修改邮箱账号、密码或腾讯/Namecheap 服务参数。
- 不改变 IMAP 首次同步最近三十天邮件的范围。
- 不把定时同步迁移到 Web 请求进程。
- 不新增数据库表或迁移。

## 方案

### 状态计算

新增单一的邮箱同步状态计算函数，输入为 `lastErrorCode`、`lastSyncedAt` 和当前时间，输出管理员可读的状态：

1. 存在错误码：显示现有的分类错误提示。
2. `lastSyncedAt` 为空：显示“尚未运行同步，请点击立即收取邮件”。
3. 最近同步时间距当前时间超过十分钟：显示“自动同步可能未运行，请检查后台 Worker”。
4. 其他情况：显示“同步正常”。

十分钟阈值覆盖正常的两分钟调度以及短暂任务延迟，避免偶发延迟造成误报。

邮箱列表和邮箱详情必须复用同一状态函数，避免出现左侧“尚未同步”、右侧“同步正常”的矛盾。

### 页面信息

- “最近连接测试”继续显示 `lastTestedAt`。
- “最近成功收信”改为“最近成功同步”，并显示 `lastSyncedAt`。
- 第三个摘要项显示“自动同步频率：每 2 分钟”，不再把通用的 `lastSuccessAt` 当作收信时间。
- 连接测试成功提示改为：“收信和发信连接均正常；测试连接不会收取邮件。”
- 首次同步仍由“立即收取邮件”按钮触发；成功后刷新页面并显示收到、关联和未匹配数量。

### 部署检查

部署文档明确要求 Web 与 Worker 同时启动，并增加排查顺序：

1. 检查 `recall-worker` 容器是否运行且健康。
2. 检查 Worker 日志是否已注册 `mail-sync` 调度或出现分类同步错误。
3. 点击“立即收取邮件”验证 Web 侧手动同步链路。
4. 等待两到四分钟后刷新页面，确认 `lastSyncedAt` 自动推进。

## 错误处理

现有错误分类保持不变。IMAP 鉴权、超时、TLS、收件箱读取和邮件处理错误继续写入 `lastErrorCode`。状态函数始终优先展示这些错误，只有没有错误时才判断从未同步或同步停滞。

## 测试

按照测试驱动方式增加覆盖：

1. 无错误但从未同步时显示“尚未运行同步”。
2. 最近同步时间超过十分钟时显示 Worker 告警。
3. 十分钟内成功同步时显示“同步正常”。
4. 分类错误优先于时间状态。
5. 邮箱详情正确显示最近成功同步和自动同步频率。
6. 连接测试成功提示明确说明不会收取邮件。
7. 现有手动同步接口与 Worker 同步集成测试继续通过。

## 验收标准

- 截图中的矛盾状态不再出现。
- 管理员无需查看代码即可知道测试连接与实际收信的区别。
- Worker 未运行时，页面最迟在十分钟阈值后给出明确告警。
- 点击“立即收取邮件”成功后，即使收到零封邮件，也显示最新同步时间。
- Lint、类型检查、单元测试和生产构建全部通过。
