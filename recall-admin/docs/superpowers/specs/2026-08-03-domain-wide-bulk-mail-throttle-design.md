# 域名级群发随机间隔设计

## 背景

当前群发任务会连续处理收件人，并在一批完成后立即调度下一批。大量邮件集中投递到 QQ 邮箱时，可能触发 `550 Domain frequency limited`。腾讯按发件域名统计频率，因此仅在单个群发任务内部限速，或更换同一域名下的发件邮箱，都不能形成可靠保护。

## 目标

- 同一发件域名下的所有群发邮件共享发送节奏。
- 任意两次群发投递尝试之间随机间隔 2–4 分钟，包含边界值。
- 首次符合条件的群发邮件可以立即发送。
- 多群发任务、多发件邮箱、多工作进程和服务重启都不能绕过间隔。
- 单封人工邮件和人工回复不受群发间隔影响。

## 非目标

- 不提供管理员自定义间隔的界面。
- 不改变收件人分组、模板、退订、暂停联系或重复邮箱过滤规则。
- 不在本次改动中重新设计 SMTP 错误分类或自动重试策略。
- 不通过切换同域名邮箱规避服务商限制。

## 方案选择

采用数据库级“发件域名发送闸门”。进程内计时会在服务重启后丢失，单批次计时则会被并行群发任务绕过；数据库中的域名状态可以为所有任务和工作进程提供同一事实来源。

## 数据模型

新增域名群发节流记录，每个规范化发件域名仅有一条：

- `senderDomain`：小写规范化域名，唯一键。
- `nextAvailableAt`：该域名下一次允许尝试群发的时间。
- `createdAt`、`updatedAt`：审计与运维时间。

发件域名从群发所选邮箱的发件地址中提取。例如 `alisa@righttoken.ai` 和 `contact@righttoken.ai` 都映射到 `righttoken.ai`。

## 调度与并发流程

1. 创建群发时仍立即调度任务，用户操作方式不变。
2. 工作任务读取群发所选邮箱并确定规范化发件域名。
3. 在数据库事务中锁定该域名的节流记录，确保并发任务串行争用同一个闸门。
4. 如果 `nextAvailableAt` 晚于当前时间，本次不领取收件人，并把任务延迟到该时间后再运行。
5. 如果域名当前可发送，事务只领取一位 `PENDING` 收件人，并生成 120–240 秒的随机间隔。
6. 事务在发送前把 `nextAvailableAt` 更新为当前时间加随机间隔，然后提交。
7. 事务提交后执行 SMTP 投递并更新该收件人的结果。
8. 群发仍有待发送收件人时，任务按数据库中的下一次允许时间重新调度。

每次任务最多领取一位收件人。数据库锁和先预约后发送的顺序保证多个群发任务、多个邮箱和多个工作进程不能在同一域名闸门下同时领取发送资格。

## 失败处理

- 无论 SMTP 投递成功还是失败，该次尝试都消耗已预约的 2–4 分钟间隔。
- 这样可以避免拒收或网络错误后立即高频撞击收件服务商。
- 现有失败状态和人工重试入口保留；重新进入队列的失败邮件仍必须经过域名发送闸门。
- 如果任务在预约后、SMTP 调用前崩溃，收件人的现有陈旧领取恢复机制继续负责收敛状态，域名闸门不会提前释放。

## 调度接口

群发调度接口增加可选的 `runAt` 时间。生产任务调度器把它映射为延迟执行时间；现有创建群发和人工重试可以省略该值，以便立即进入闸门检查。

随机数生成作为依赖注入到群发处理函数，生产环境使用系统随机数，测试使用固定值，从而精确验证 120 秒、240 秒及中间值。

## 用户体验

- 写邮件、选择分组、创建群发和查看批次的页面保持不变。
- 群发状态会随着每封邮件逐步更新。
- 平均间隔约 3 分钟，即每小时约 20 封；875 封平均约需 44 小时，理论范围约 29–58 小时。
- 单封人工发送和人工回复维持即时处理。

## 测试范围

- 随机间隔始终落在 120–240 秒并覆盖边界。
- 同一域名下不同邮箱共享一个节流记录。
- 同一域名下不同群发任务不能同时领取发送资格。
- 不同发件域名拥有相互独立的节奏。
- 未到允许时间时不发送，并按正确时间重新调度。
- 成功和失败的 SMTP 尝试都会推进下一次允许时间。
- 人工重试仍经过群发闸门。
- 单封人工邮件和回复路径不读取群发闸门。
- 数据库迁移、单元测试、集成测试、类型检查、代码检查和生产构建全部通过。
