# 邮件中心可编辑收件人设计

## 背景与目标

邮件中心当前只能把任务关联用户的邮箱作为最终收件人，无法在首次邮箱联调或特殊人工处理时改用另一个邮箱。目标是在不取消任务关联、权限检查和退订保护的前提下，允许所有具有邮件发送权限的成员编辑最终收件邮箱。

## 用户体验

邮件编辑器继续要求选择一个任务和一个已启用邮箱。选择任务后，收件邮箱默认填入任务用户邮箱，但输入框不再只读，主管理员、管理员和运营都可以修改。

当最终收件邮箱不同于任务用户邮箱时，编辑器显示“手动收件人”提示，说明本次发送仍会关联当前任务，并会记录修改后的实际收件地址。切换任务时，收件邮箱重置为新任务用户邮箱，避免把上一位用户的地址误带到下一项任务。

发送成功后继续显示统一的成功提示并刷新邮件记录。邮箱格式无效、任务或邮箱缺失、存在未替换变量时，发送按钮不可用。

## 权限与安全规则

- 所有具有 `mail:send-reviewed` 权限的成员均可编辑最终收件邮箱。
- 运营人员仍只能对自己负责的任务或自己负责的用户发送邮件；编辑收件人不改变任务权限边界。
- 任务用户处于暂停或退订状态时，无论收件邮箱是否修改，都禁止发送。
- 系统还会按最终收件邮箱查询全局退订名单；命中时禁止发送。
- 频率限制继续按任务用户的历史触达记录执行，避免通过更换收件邮箱绕过频控。
- 主题、正文、未替换变量、空内容和已启用邮箱检查保持不变。
- 前端提示只用于改善体验，全部安全规则必须由服务端再次执行。

## 服务端数据流

`POST /api/mail/send` 请求新增必填的 `recipient` 字段。接口使用标准邮箱格式校验，并将规范化后的地址传给邮件发送服务。

发送服务仍加载成员、邮箱、任务和用户，并执行现有任务权限检查。随后同时检查：

1. 任务用户的暂停和退订状态；
2. 任务用户邮箱是否在全局退订名单；
3. 最终收件邮箱是否在全局退订名单；
4. 任务用户的最近发送时间和频率限制。

邮件草稿和最终发送记录继续关联原任务与原用户，但 `toAddresses` 保存实际收件邮箱。SMTP 适配器只向 `toAddresses` 中记录的最终地址发送。

审计日志增加：

- `recipientOverridden`：最终地址是否不同于任务用户邮箱；
- `recipientDomain`：最终收件域名；
- `originalRecipientDomain`：任务用户邮箱域名。

审计元数据不额外复制完整邮箱，完整实际地址只保留在受权限保护的邮件记录中。

## 回复匹配

用户直接回复原邮件时，系统优先使用 `In-Reply-To` 和 `References` 匹配已发送邮件，因此手动收件地址的回复仍能回到原任务和用户。

如果邮件服务商未保留回复头，系统才回退到发件人、邮箱和主题匹配。手动收件地址与用户资料邮箱不同时，这种回退可能进入人工归档箱；系统不得为了提高命中率而自动修改用户资料邮箱。

## 错误处理

- 无效收件邮箱返回 `INVALID_MAIL_SEND_REQUEST`。
- 最终邮箱命中退订名单返回 `RECIPIENT_SUPPRESSED`。
- 任务用户暂停、退订或频率限制继续返回现有稳定错误码。
- SMTP 失败时草稿标记为 `FAILED`，保存稳定错误码，不在响应中暴露凭据或供应商原始错误。

## 测试标准

### 单元测试

- 编辑器默认使用任务用户邮箱。
- 手动修改后显示提示并提交最终地址。
- 切换任务时重置为新任务邮箱。
- 无效邮箱和未替换变量阻止提交。

### 集成测试

- 服务端把手动地址交给 SMTP 适配器，并把实际地址写入 `toAddresses`。
- 邮件记录仍关联原任务和用户。
- 运营人员不能借修改地址发送不属于自己的任务。
- 任务用户退订或暂停时，修改地址仍无法发送。
- 最终地址命中全局退订名单时无法发送。
- 审计日志正确标记收件人是否被修改。

### 回归测试

- 未修改收件人时，现有审核发送、频率限制和邮件记录行为保持不变。
- 直接回复手动收件邮件时，回复头匹配仍回到原任务。
- 邮件中心、设置页和任务流程端到端测试保持通过。

## 非目标

- 不允许无任务发送普通运营邮件。
- 不自动修改用户资料中的邮箱。
- 不增加群发、抄送、密送或附件功能。
- 不允许绕过暂停、退订、任务权限或频率限制。
